1它解决什么

一句话

常驻全量 ftrace 抓取最贵的不是落盘，而是 把内核 ftrace 二进制页解析成 protobuf 的常驻 CPU。本方案让常驻期只搬运不解析（页进每 CPU 环形缓冲），仅在触发时才解析落盘——常驻 CPU 实测从 ~39% 降到 ~8%（约 80%），IO 归零，内存以硬上限管控。

背景是机器人稳定性排查：问题往往转瞬即逝，事后再开 trace 已经晚了；而 traced/traced_probes 常驻全量采集又会在 CPU/IO 上压垮系统。

真正的矛盾在于：要保留"触发前 N 秒"的现场，这 N 秒的数据在触发之前就必须已经在缓冲区里——你无法事后回放没采过的过去。所以"前 N 秒高保真"与"常驻零开销"在物理上冲突。本方案的破法是改变常驻期的采集形态：内核 ftrace 页常驻期只 memcpy 进用户态环形缓冲、跳过解析，触发时（由业务发 CLONE_SNAPSHOT 触发）才一次性解析进 trace 并被克隆落盘。前 N 秒来自环形缓冲，后 M 秒来自触发后的 stop_delay_ms 延迟窗口。

读者路径只想部署：直接看 §2 + §4 配置参考。想懂为什么这么设计：§3 架构。要改代码 / 排障：§5 实现 + §7 边界。所有结论的可信度都用 verified（真机实测/源码核对）/ inferred（合理推断）/ unknown 标注。

2快速部署

部署只需三步：放一份 trace config、让业务在异常时发一个具名触发、到约定路径取快照文件。不需要写代码——能力都在配置层。

前置条件

目标机需要满足两点，缺一不可 verified（本项目在内核 6.8 + 真实 tracefs 的机器上验证）：内核挂载了 tracefs（/sys/kernel/tracing），且 Perfetto 版本支持 CLONE_SNAPSHOT（v38+ / Android V+）。前者是 ftrace 的前提，后者是"触发即克隆快照"机制的前提——更老的 Perfetto 没有这个触发动作，缓存的页永远不会被解析。

内存护栏（最易踩的坑）每 CPU 缓冲上限 × CPU 数 必须落在 traced_probes 内存看门狗内（默认 ~32 MB），否则进程被自身看门狗杀掉 verified。曾用 per_cpu_mem_limit_kb=8192 在 128 核机上分配到 358 MB → 被杀；降到 256 KB/核（总 ≤32 MB）即正常。核越多，每核缓冲越要小——大窗口靠 §4 的磁盘溢出或进程过滤承接。

配置 / 触发 / 取快照

用下面这份机器人综合配置启动一个常驻会话（perfetto -c robot.cfg --txt -o /data/snap.pftrace）。它常态等待触发，不落盘；触发到来后，把"前 N + 后 M 秒"写成带计数后缀的快照文件（snap.pftrace.0、.1…）。

buffers { size_kb: 131072 fill_policy: RING_BUFFER }   # 须能容纳 N+M 秒解析量
data_sources { config {
  name: "linux.ftrace"
  ftrace_config {
    ftrace_events: "sched/sched_switch"
    ftrace_events: "irq/irq_handler_entry"
    ftrace_events: "raw_syscalls/sys_enter"      # 通路C：详细 ftrace 直接列在这里
    deferred_raw_capture {
      enabled: true
      per_cpu_mem_limit_kb: 256                   # × 核数 ≤ ~32MB 看门狗
      retain_seconds: 30                          # 从快照时刻往回的窗口
      # disk_overflow_path: "/data/perfetto/draw" # 可选：大窗口溢出到磁盘
      # per_cpu_disk_limit_kb: 4096
    }
    pid_filter_control_file: "/run/perfetto/ftrace_pid_filter"  # 可选：动态进程过滤
  }
}}
trigger_config {
  trigger_mode: CLONE_SNAPSHOT
  trigger_timeout_ms: 86400000
  triggers { name: "snap" stop_delay_ms: 2000 }  # 后 M 秒 = 2s
}

业务发现异常时，主动发 snap 触发——这是设计上唯一的触发方式（机器人自有健康判定，不内置检测器）。两种等价做法：

进程内（SDK）

业务自己的进程里一行即可：

Tracing::ActivateTriggers({"snap"});

最直接，无需外部进程。

脚本 / 外部进程（CLI）

用一份仅含 activate_triggers 的配置：

perfetto -c snap_trigger.cfg --txt
# snap_trigger.cfg 内容：
#   activate_triggers: "snap"

注意 perfetto 没有 --trigger 选项 verified。

动态进程过滤（可选，HTTP-ready）若只关心某些进程，往 pid_filter_control_file 写目标 PID 列表（每行一个），traced_probes 约 1s 内拾取并重写内核 set_event_pid，运行时增删 PID 即时生效。HTTP/gRPC 服务只需写这个文件即可接入。实测：运行中写入目标 PID → 其全部线程被动态捕获 verified。

3架构与机制

方案按数据源特性分三条通路，汇入同一份快照；只有"全量重型 ftrace"那条做了真改造，其余复用 Perfetto 原生能力。

通路划分 三路汇入单快照
A · 低开销源SDK + 低频 ftrace
→
B · 全量重型 ftracedeferred-raw 旁路（唯一改造）
→
C · 详细 ftrace纯配置，折入 B 的事件集
A 走原生解析（开销本就低）；C 只是在配置里多列事件，和 B 一起常驻缓存、触发时进同一快照；B 是核心改造。
触发到来
通路 B · deferred-raw 生命周期 常驻搬运 → 触发解析
read() 内核页memcpy 进每CPU环形buf跳过解析（常驻 CPU≈搬运）
触发 +M 秒：CLONE_SNAPSHOT 发 kTraceClone flush 给 traced_probes
解析：FtraceController 用 table/symbolizer 把窗口内页分批解析进 TraceWriter
克隆落盘：service buffer 被克隆为快照文件
解析挂在原生 clone-flush 钩子上：先把页解析进 writer 并提交，再 ack flush，service 克隆时数据已就位。

三个决定性的设计点

第一，前后都要全量高保真排除了"常驻降频采样"，所以降常驻 CPU 只剩"延迟解析"一条路——常驻期把页留在缓冲里不解析，触发时才解析。第二，内核 ftrace 时钟域：页时间戳与 GetBootTimeNs() 仅在 trace_clock=boot 时同域，所以按时间裁剪（retain_seconds）只在 boot 时钟启用，其它时钟回退全量解析 verified。第三，触发瞬间的内存峰值并不省：解析后的 protobuf 仍要经 service buffer 才被克隆，故 buffer.size_kb 须能容纳 N+M 秒解析量——常驻内存省了，峰值不省，这是必须知道的取舍。

为什么这样能成立内核 ftrace 页本就是自包含的二进制；memcpy 一页的成本远低于把页里每个事件解析成 protobuf。把"解析"从常驻期挪到触发那一刻，就把持续的 CPU 成本变成了一次性的峰值——而峰值发生时业务已经在出问题、本就要抓现场，这一刻的 CPU 花得值。

5实现

改造集中在 traced_probes 侧的 ftrace 子系统，不动 tracing_service_impl.cc 的核心——触发、CLONE、clock snapshot 全复用原生。下表是关键文件与职责。

文件作用

触发解析为何挂在 flush 钩子上

关键时序是：CLONE_SNAPSHOT 克隆的是 service 端 buffer，克隆前会给所有 producer 发一次 Reason::kTraceClone 的 flush，并在收到 ack 后才复制。所以把"解析 raw → 写 TraceWriter → 提交"放在这次 flush 的回调里、ack 之前完成，数据就会在克隆时已落入 service buffer。ProbesProducer::Flush 识别 kTraceClone 标记数据源，FtraceDataSource::OnFtraceFlushComplete 在 writer_->Flush() 前调 FtraceController::ParseDeferredRawForClone——后者持有解析所需的 ProtoTranslationTable 与 symbolizer，逐 CPU 把窗口内页分批（32 页/批）喂给现有 ProcessPagesForDataSource，从而与稳态解析输出完全一致。

代码审查修掉的真问题全分支审查发现并已修复 verified：① 动态过滤 watcher 捕获的 Tracefs* 在 secondary instance 销毁时悬垂（UAF）→ 绑定到 owning data source 提前释放；② 磁盘 IO 用 PERFETTO_CHECK，磁盘满即 abort 守护进程 → 改优雅降级 + EINTR；③ 触发解析曾把整窗口拼成单个连续 buffer（抵消 spill、OOM 风险）→ 改 32 页分批，峰值内存有界；④ 磁盘溢出文件从不删除 → open-then-unlink 自动回收。

6实测验证

以下数据均来自真机（内核 6.8 / 128 核 / 真实 tracefs）跑完整 traced+traced_probes+perfetto 栈 verified。它们是"降开销"命题的直接证据，而非估算。

场景指标结果置信
一个被识破的伪回归排查中曾见所有 trace 压成 ~40 事件，差点误判为代码 bug；用对照实验（普通配置也只有 23 事件）+ 直接读 tracefs 状态，定位到是上一个测试在 set_event_pid 留下的过滤残留（指向 PID 1）。这也印证一个运维点：强杀 traced_probes 会残留 tracefs 过滤状态（对所有 ftrace 配置都一样，非本改造独有），干净停止时 muxer 会清。

7兼容性与边界

对外完全兼容（标准 trace、版本前后兼容、GN/Android/Bazel 三套构建均已同步）；对内，进程过滤按 Perfetto 既有约定是独占特性，deferred-raw 可与其他会话并存。

兼容 verified

trace 格式：快照是标准 Perfetto trace，trace_processor/UI 正常读。版本：新 proto 字段全 optional，前后向兼容。并发会话：deferred_raw 不动全局 tracefs 状态，CpuReader 把页路由给所有数据源，可与普通会话并存。构建：gen_all 已同步 Android.bp + bazel BUILD。

边界 / 待知

进程过滤是独占特性：它改全局 set_event_pid，Perfetto 强制单租户（已把 pid_filter_control_file 补进 HasExclusiveFeatures）。非 boot 时钟：retain_seconds 时间裁剪仅 boot 时钟生效，其它回退全量解析 inferred（按时钟域推断，未在非 boot 机型实测）。超大窗口：解析仍同步运行，retain_seconds 已界定其量，但极大窗口下彻底消除 watchdog 风险需异步让步（未做）。
